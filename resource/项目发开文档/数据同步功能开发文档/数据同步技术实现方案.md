# 企业级数据同步完整指导书

> 适用场景：外部系统 → 本地，实习项目练手，企业级落地参考。
> 写给"看得懂 Spring Boot，但没做过生产级数据同步"的同学。

---

## 〇、先建立全局视图

数据同步的本质是 **"把 A 系统里变了的数据，按正确的顺序、可恢复的方式、搬运到 B 系统"**。看似一句话，但里面每一个词都是坑：

| 词 | 真正的工程问题 |
| --- | --- |
| 变了的数据 | 怎么识别？靠时间戳、版本号、变更日志，还是全量对比？ |
| 正确的顺序 | 多表之间有依赖（比如订单 → 订单行），乱了怎么补？ |
| 可恢复的方式 | 网络抖、目标库宕机、目标库写一半挂了，怎么续跑？ |
| 搬运 | 一次拉多少？失败要不要重试？幂等怎么保证？ |

下面所有的模式、设计、踩坑，都是在解决这四件事。

## 一、同步模式全景（架构选型先看这张图）

### 1.1 按触发方式分

| 模式 | 谁发起 | 典型场景 |
| --- | --- | --- |
| **拉模式（Pull）** | 本地定时调外部 | 外部不配合、跨组织、跨网络 |
| **推模式（Push）** | 外部主动调/发 MQ | 内部系统间、实时性要求高 |
| **混合（CDC）** | 数据库日志订阅 | 同库不同库、强一致 |

你的场景（外部 → 本地）几乎一定是 **拉模式 + 定时**。

### 1.2 按数据量分

| 模式 | 适用 | 风险 |
| --- | --- | --- |
| **全量同步** | 数据量小（< 100 万）、首次同步 | 大表会很慢；外部系统压力大 |
| **增量同步** | 数据量大、有变更字段 | 漏单是最大风险 |
| **全量 + 增量** | 首次全量，之后增量 | **企业级事实标准**，下面重点讲 |

## 二、增量检测机制（你最该搞懂的选型）

### 2.1 时间戳方案（updated_at / modify_time）

**原理**：每次同步拉 `WHERE updated_at > 上次同步时间`。

```sql
-- 伪代码
SELECT * FROM external_supplier
WHERE updated_at > #{lastSyncTime}
ORDER BY updated_at ASC
LIMIT 1000
```

**优点**：简单，95% 场景适用。
**缺点**：
- **时钟踩坑**：外部系统不同节点时钟可能不一致；同一毫秒多条更新可能漏；时区问题
- **物理删除看不见**：删除一条记录，更新时间不会变
- **回填踩坑**：补历史数据时，更新时间全是"现在"，会把上游所有数据当成新增

**适用**：能保证单调递增、且不依赖"真删除"的业务表。

### 2.2 递增 ID / 版本号方案

**原理**：外部系统提供单调递增的 `id` 或 `version`，本地只拉 `id > lastId`。

```sql
SELECT * FROM external_supplier
WHERE id > #{lastId}
ORDER BY id ASC
LIMIT 1000
```

**优点**：精准、无时钟问题、性能好（索引扫描）。
**缺点**：
- 外部系统必须保证单调（不重不漏）
- 物理删除仍然看不见（除非外部配合 `deleted_at`）

**适用**：能拿到自增主键或版本号的标准表。

### 2.3 快照对比方案（Hash/指纹）

**原理**：每次拉一页数据，对每行算指纹（hash(主键+关键字段)），与上次对比。

**适用**：外部系统没有 `updated_at`，只有 GET 接口。
**缺点**：成本高，需要本地缓存上次指纹；变更检测是 N×N。
**不推荐作为主流方案**，仅作为兜底。

### 2.4 事件订阅方案（CDC / MQ）

**原理**：外部系统在数据变更时把变更事件发到 MQ，本地消费即可。

**适用**：内部系统、强实时、外部有改造能力。
**你的场景不适用**（外部不配合）。

### 2.5 数据库日志订阅（CDC：Canal / Debezium）

**原理**：伪装成外部库的从库，订阅 binlog，拿到所有变更。

**适用**：同网络、能直连外部库。
**优点**：捕获所有变更（包括 DELETE）、实时。
**缺点**：对外部库侵入大；权限敏感；schema 变更难处理。

### 2.6 选型建议（你的项目）

**首选：版本号/递增 ID 方案**（如果外部能提供）
**次选：时间戳方案**（最通用，但要补"软删除"和"漏单"两个补丁）
**企业级兜底：全量 + 增量 + 定期对账**

## 三、企业级同步引擎的 6 大模块

无论选什么增量机制，一个能上生产的同步引擎必须包含这 6 块：

```
┌─────────────────────────────────────────┐
│  1. 任务定义层：哪些表、什么频率、什么规则   │
├─────────────────────────────────────────┤
│  2. 抽取层：调用外部 API/DB/文件          │
├─────────────────────────────────────────┤
│  3. 转换层：清洗、映射、字段加工           │
├─────────────────────────────────────────┤
│  4. 写入层：批量 upsert，处理冲突          │
├─────────────────────────────────────────┤
│  5. 状态层：水位线、批次、失败重试          │
├─────────────────────────────────────────┤
│  6. 监控层：指标、告警、补偿               │
└─────────────────────────────────────────┘
```

### 3.1 任务定义层（最容易被忽视）

不要硬编码"同步哪些表"，写成配置 + 注册中心模式：

```yaml
sync:
  tasks:
    - code: supplier-from-sap
      source: sap-supplier-api
      targetTable: agg_supplier
      incremental:
        type: timestamp        # timestamp | id | hash
        field: updated_at
      schedule: "0 0/10 * * * *"  # 每 10 分钟
      batchSize: 500
      retry:
        maxAttempts: 3
        backoff: exponential
```

**为什么重要**：生产上同步任务会越来越多，配置化才能批量管理。

### 3.2 抽取层（Source Connector 模式）

把"如何拉数据"封装成统一的接口：

```java
public interface SourceConnector<T> {
    // 拉一页数据，返回这页 + 是否有下一页
    SourcePage<T> fetch(SourceCursor cursor, int batchSize);
}

public record SourcePage<T>(List<T> records, SourceCursor nextCursor, boolean hasMore) {}
```

实现可以有：`RestSourceConnector`、`JdbcSourceConnector`、`FileSourceConnector`、`MqSourceConnector`。
**好处**：换数据源只换实现，业务逻辑不变。

### 3.3 转换层（可插拔的 transformer）

```java
public interface RecordTransformer<S, T> {
    T transform(S source);
}
```

经典加工：
- 字段重命名
- 编码转换（GBK → UTF-8）
- 字典翻译（外部 code → 内部 id）
- 脱敏（身份证、银行卡）
- 业务校验（金额非负、状态合法）

### 3.4 写入层（幂等 upsert 是关键）

**核心原则：必须幂等**。同步失败重试是常态。

```sql
-- MySQL 幂等写入：ON DUPLICATE KEY
INSERT INTO agg_supplier (external_id, name, updated_at)
VALUES (?, ?, ?)
ON DUPLICATE KEY UPDATE
  name = VALUES(name),
  updated_at = VALUES(updated_at);

-- PostgreSQL：ON CONFLICT
INSERT INTO agg_supplier (external_id, name, updated_at)
VALUES (?, ?, ?)
ON CONFLICT (external_id) DO UPDATE SET
  name = EXCLUDED.name,
  updated_at = EXCLUDED.updated_at;
```

**踩坑提醒**：
- 一定要有 `external_id` 唯一约束（或者再加一个 `_sync_task_code` 做联合唯一键，防止多任务冲撞）
- 软删除：用 `is_deleted` 字段，不要物理删除
- 批量大小：MySQL 默认 `max_allowed_packet` 4M，批太大报错

### 3.5 状态层（同步的"记忆"）

**最核心的一张表：`sync_checkpoint`**

```sql
CREATE TABLE sync_checkpoint (
  task_code       VARCHAR(64)  PRIMARY KEY,
  cursor_value    VARCHAR(128),           -- 水位线值（时间戳或 ID）
  last_batch_id   VARCHAR(64),            -- 上一批的批次 ID
  last_success_at DATETIME,
  last_error      TEXT,
  status          VARCHAR(32),            -- RUNNING / SUCCESS / FAILED
  version         BIGINT                   -- 乐观锁，防并发跑
);
```

**关键操作流程**：

```
1. SELECT ... FROM sync_checkpoint WHERE task_code = ? FOR UPDATE
2. 拉取一批数据（用 cursor_value）
3. 写入目标库（幂等）
4. UPDATE sync_checkpoint SET cursor_value = 新游标, status='SUCCESS'
5. COMMIT
```

**踩坑**：
- 必须用行锁（`SELECT FOR UPDATE` 或 Redis 分布式锁），**否则多实例并发会重复拉**
- 每一步异常都要更新 `status=FAILED` + `last_error`，否则排错抓瞎
- 游标要"成功后"才推进，否则失败重试会丢数据

### 3.6 监控层（企业级和 demo 的分水岭）

必上指标（Micrometer + Prometheus）：

| 指标 | 含义 | 告警建议 |
| --- | --- | --- |
| `sync.task.duration` | 单次任务耗时 | > SLA 阈值告警 |
| `sync.task.last.success.timestamp` | 上次成功时间 | 超 N 分钟没成功 → 告警 |
| `sync.records.processed.total` | 处理行数 | 突增/突降告警 |
| `sync.error.count` | 失败次数 | > 阈值告警 |
| `sync.cursor.lag` | 游标滞后时间 | > N 分钟告警 |

必看告警：
- **同步停滞**：上次成功到现在超过 2 倍周期
- **连续失败**：同一任务连续失败 N 次
- **数据量异常**：单次同步量 < 历史均值的 10%，可能漏单

## 四、调度系统选型

### 4.1 三种主流方案对比

| 方案 | 适用 | 缺点 |
| --- | --- | --- |
| **Spring `@Scheduled` + 单实例** | 学习阶段、单实例部署 | 不支持分布式、不可视化 |
| **Quartz** | 中型项目、需复杂调度 | 集群配置复杂 |
| **XXL-Job** | 国内企业首选 | 多一个组件要维护 |
| **Elastic-Job** | 大型项目、需分片 | 学习成本高 |

### 4.2 推荐：XXL-Job（国内企业事实标准）

原因：
1. **可视化**：Web 控制台直接 CRUD 任务、查看执行历史
2. **分布式**：调度中心 + 执行器，多实例只跑一次
3. **失败重试**：内置
4. **分片广播**：大任务可以拆 N 个分片并行

**和你项目的契合度**：完美。XXL-Job 部署一个独立调度中心，你的 aggregation-service 注册成执行器即可。

### 4.3 调度上必须解决的 3 个问题

1. **分布式互斥**：多实例只跑一次（用 DB 行锁 / Redis 锁 / XXL-Job 自带）
2. **超时控制**：单批必须有超时（防止一直挂住）
3. **错过执行**：宕机错过的任务要不要补跑？（一般补，但要看业务）

## 五、可靠性保障（企业级必上清单）

### 5.1 至少一次 vs 恰好一次

| 保证级别 | 含义 | 实现方式 |
| --- | --- | --- |
| **At-most-once** | 不重不漏（理论） | 不重试、不重发 |
| **At-least-once** | 可能重复 | 重试 + 幂等写入 ✅ **企业主流** |
| **Exactly-once** | 真恰好一次 | 几乎不可能，分布式理论上限 |

**实战选择**：**At-least-once + 幂等写入** = 用户体验等价于 Exactly-once。

### 5.2 幂等的 4 层防御

1. **业务唯一键**：`external_id + sync_task_code` 做联合唯一约束
2. **写入幂等**：upsert 而不是 insert
3. **游标幂等**：批次带 `batch_id`，重放可以识别
4. **对账兜底**：定期全量对账（diff），找出漏单的少量数据补

### 5.3 死信 + 补偿

```java
// 失败超过 maxAttempts → 进死信表，不无限重试
sync_dead_letter (
  task_code, batch_id, payload, error,
  retry_count, next_retry_at, created_at
)
```

死信处理：
- 人工 / 半自动补偿（推荐：报警 + 提供 UI 重跑）

### 5.4 对账机制（终极兜底）

每天 / 每周跑一次全量对账：

```sql
-- 找出外部有、本地没有的（漏单）
SELECT external_id FROM external_supplier
EXCEPT
SELECT external_id FROM agg_supplier;

-- 找出本地有、外部没有的（孤儿，多半是物理删除漏处理）
SELECT external_id FROM agg_supplier
EXCEPT
SELECT external_id FROM external_supplier;
```

对账发现的差异进 review 队列，由人工或脚本兜底。

## 六、经典踩坑点（前人血泪）

### 6.1 时钟问题

- **坑**：外部系统多节点时钟漂移，导致 `updated_at` 倒退
- **解**：水位线推进时取 `MAX(waterline, newValue - 1s)`，留 1 秒 buffer

### 6.2 物理删除看不见

- **坑**：外部删了记录，本地还有残留
- **解 A**：要求外部配合 `deleted_at` 软删除
- **解 B**：定期对账，识别孤儿
- **解 C**：全量同步时按主键覆盖（成本高）

### 6.3 长事务 / 长批写入

- **坑**：一次同步 10 万行，单 SQL 卡死
- **解**：批大小 500~2000，事务只包一批，失败不影响后续

### 6.4 网络抖动 / 外部超时

- **解**：重试 + 指数退避 + 熔断（Sentinel / Resilience4j）

### 6.5 Schema 漂移

- **坑**：外部加字段你没发现，写入时缺字段
- **解**：抽取层做 schema 校验，字段缺失报警

### 6.6 大量历史数据回填

- **坑**：第一次同步时表里有 500 万数据，按 `updated_at > '1970'` 拉一堆
- **解**：首次全量（不带 where 条件）单独跑，之后切增量；游标初始化时记录起点

### 6.7 同步任务互斥

- **坑**：XXL-Job 多实例同时跑 → 重复拉、重复写
- **解**：调度层互斥 + 状态表 `SELECT FOR UPDATE` 双重保险

### 6.8 事务边界错误

- **坑**：把同步、转换、写入、状态推进放一个大事务 → 失败全回滚，状态不推进，死循环
- **解**：每个批次独立事务；状态推进必须独立提交

### 6.9 时间窗口重叠

- **坑**：定时 10 分钟跑一次，单次跑 12 分钟，下次启动和上次重叠
- **解**：调度层加 `misfire` 策略；或者上一次未跑完直接跳过（看业务）

### 6.10 数据倾斜

- **坑**：某个客户的数据量是其他 100 倍，同步被它卡住
- **解**：按客户分片 + 并行；或者大客户走独立任务

## 七、结合你项目的推荐实现方案

### 7.1 你的项目架构

```
domain services (supplier/procurement/sourcing/...)
        │
        ▼
aggregation-service  ← 你要在这里做"外部系统 → 本地"
   ├─ MySQL（数据汇总表，已存在）
   └─ 同步任务调度（你新增）
```

### 7.2 推荐技术选型（学习 + 企业级平衡）

| 组件 | 选型 | 理由 |
| --- | --- | --- |
| 同步框架 | **不引入 DataX / Flink CDC**，手写 | 学习价值最高，规模也合适 |
| 调度 | **XXL-Job**（你的平台已有） | 国内企业标准 |
| HTTP 客户端 | **Spring RestTemplate 或 WebClient** | 已依赖 |
| 数据库 | **MySQL**（你项目已用） | upsert 语法简单 |
| 幂等 | **联合唯一键 + batch_id** | 不需要额外组件 |
| 监控 | **Spring Boot Actuator + Micrometer** | 你的父 POM 已有依赖 |
| 限流/熔断 | **Sentinel** 或 Resilience4j | 你已有 Spring Cloud Alibaba 生态 |

### 7.3 最小可落地代码骨架（伪代码）

```java
// 1. 任务执行器（XXL-Job 调度入口）
@XxlJob("syncSupplierFromSap")
public void syncSupplier() {
    String taskCode = "supplier-from-sap";
    SyncCheckpoint cp = checkpointService.lockAndGet(taskCode); // 行锁
    
    try {
        int batchNo = 0;
        SourceCursor cursor = cp.getCursor();
        while (true) {
            // 抽取
            SourcePage<SapSupplier> page = sapConnector.fetch(cursor, 500);
            if (page.isEmpty()) break;
            
            // 转换
            List<AggSupplier> targets = page.getRecords().stream()
                .map(transformer::transform)
                .toList();
            
            // 幂等写入（事务独立）
            writer.upsertBatch("agg_supplier", targets);
            
            // 推进游标（独立提交）
            cursor = page.getNextCursor();
            checkpointService.updateCursor(taskCode, cursor, batchNo);
            
            batchNo++;
            if (!page.hasMore()) break;
        }
        checkpointService.markSuccess(taskCode);
    } catch (Exception e) {
        checkpointService.markFailed(taskCode, e);
        deadLetterService.save(taskCode, e);
        throw e; // 让 XXL-Job 走重试
    }
}
```

### 7.4 数据库表设计

```sql
-- 1. 同步状态表
CREATE TABLE sync_checkpoint (
    task_code        VARCHAR(64)  PRIMARY KEY,
    cursor_value     VARCHAR(128),
    last_batch_id    VARCHAR(64),
    last_success_at  DATETIME,
    last_error       TEXT,
    status           VARCHAR(32),
    version          BIGINT       DEFAULT 0,
    updated_at       DATETIME     DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
);

-- 2. 死信表
CREATE TABLE sync_dead_letter (
    id            BIGINT AUTO_INCREMENT PRIMARY KEY,
    task_code     VARCHAR(64),
    batch_id      VARCHAR(64),
    payload       MEDIUMTEXT,
    error_message TEXT,
    retry_count   INT DEFAULT 0,
    status        VARCHAR(32) DEFAULT 'PENDING',  -- PENDING / RESOLVED
    created_at    DATETIME DEFAULT CURRENT_TIMESTAMP
);

-- 3. 同步批次审计
CREATE TABLE sync_batch_log (
    id            BIGINT AUTO_INCREMENT PRIMARY KEY,
    task_code     VARCHAR(64),
    batch_id      VARCHAR(64),
    record_count  INT,
    duration_ms   BIGINT,
    status        VARCHAR(32),
    error_message TEXT,
    started_at    DATETIME,
    finished_at   DATETIME,
    INDEX idx_task_started (task_code, started_at)
);

-- 4. 目标表（举例）：外部供应商主数据 → 本地聚合
CREATE TABLE agg_supplier (
    id              BIGINT AUTO_INCREMENT PRIMARY KEY,
    external_id     VARCHAR(64) NOT NULL,
    name            VARCHAR(255),
    status          VARCHAR(32),
    source_updated_at DATETIME,
    synced_at       DATETIME DEFAULT CURRENT_TIMESTAMP,
    is_deleted      TINYINT DEFAULT 0,
    UNIQUE KEY uk_external (external_id)
);
```

### 7.5 推荐的迭代路线（你做完能在简历上写）

```
阶段 1（1~2 天）：单实例、定时、单表、upsert、无失败处理
   → 跑通最小链路

阶段 2（1 天）：加 sync_checkpoint 表，实现"成功后推进"
   → 实现真正的增量

阶段 3（1 天）：加失败重试 + 死信表
   → 实现企业级基本盘

阶段 4（1 天）：加 Micrometer 指标 + Prometheus 报警
   → 实现可观测性

阶段 5（1 天）：多实例部署 + 分布式锁
   → 实现分布式安全

阶段 6（1 天）：对账脚本 + 全量补数
   → 实现兜底保障

阶段 7（可选）：接入 XXL-Job 可视化调度
   → 实现工业级调度
```

## 九、给你的"模仿复刻"建议

你说"模仿复刻"——我理解是想学 **真正在生产用的同步方案长什么样**。我的建议：

1. **不要急着堆技术**（CDC、Flink、DataX 全上），先把手写版跑通
2. **重点学 4 个东西**：
   - **幂等写入**（upsert 的所有姿势）
   - **水位线 + 状态表**（sync_checkpoint 是灵魂）
   - **失败补偿**（死信 + 重试 + 对账）
   - **可观测性**（指标 + 告警）
3. **找一个开源项目对照看**：XXL-Job 的执行器源码（很小一段，能看完）
4. **把项目里的 aggregation-service 当成数仓 DWD 层**，目标表当成 DWS/ADS，这是最经典的离线分层 ETL 思路

跑通一个最小版，你就能在面试/简历上聊 "我做过企业级数据同步，知道水位线、幂等、补偿、对账怎么落地"，这是 **真材实料的工程能力**。
