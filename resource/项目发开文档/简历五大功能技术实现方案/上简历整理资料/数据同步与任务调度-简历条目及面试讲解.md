## 2. 业务背景与两条功能的职责

财务人员在 SAP 等外围系统维护成本中心，发生部门新增、名称调整、有效期调整、冻结、禁用等变化。SRM 采购流程使用本地副本，避免每次查询主数据都同步依赖外围响应；汇率也需要更新同币种对、同生效日的后续修订。

业务要求是周期性收敛到当前有效状态，能容忍约定的分钟级或日级延迟；没有要求捕获每一次瞬时变化或达到毫秒级实时。成本中心与汇率的周期分别配置，不把两者假定成相同 SLA。

| 简历条目 | 回答的问题 | 主要内容 |
| --- | --- | --- |
| 数据同步 | 拉哪些数据、如何正确落库、失败从哪里恢复 | 组合游标、时间窗口、业务键、批量写、页事务、对账修复 |
| 任务调度 | 何时运行、哪个实例执行、失败由谁重试 | XXL-JOB、运行状态、请求幂等、租约、心跳、执行令牌、人工补偿 |

原实习背景是金蝶云苍穹平台上的接口及插件开发，本项目是基于该业务场景的独立技术复现。讲解时区分原实习工作和后续复现增强，不将复现架构直接说成公司原生产实现。外围接口由本地模拟器演示，不声称已经连通真实 SAP。

## 3. 第一条的口述：先讲业务，再讲为什么这样选

### 3.1 一到两分钟的完整开场

> 我负责的场景是 SRM 同步外围系统维护的成本中心和汇率。成本中心不仅会新增，还会修改名称、冻结、禁用；汇率也可能修订，所以不能只同步新增记录。
>
> 选型时我比较了自增 ID、修改时间、全量指纹比较，以及 CDC 和消息队列。单独按 ID 只能发现新增，旧记录修改后 ID 不变；只用时间戳并在每页后执行“大于最后时间”，会漏掉同一时间还没读完的其他记录。全量指纹比较可以发现内容变化，但每轮仍要拉全量，不能减少源端传输。CDC 需要源数据库日志和权限配合，事件推送还需要外围可靠产生事件，当前接口边界和实时性要求没有要求我们引入这些能力。
>
> 因此选择修改时间和源表自增 ID 的组合游标：修改时间负责筛选变化，ID 负责同一时间内的稳定分页。首次按 ID 上界扫描全量，之后在固定时间窗口内按时间和 ID 排序拉增量，并用安全延迟、重叠回扫和定期全量对账处理边界及异常迟延。
>
> SRM 每页校验后批量 Upsert，把业务数据、检查点和页审计放在同一个本地事务里。失败后从最后成功页继续，重复读取通过业务键和源修改时间保护处理。页面能够查看任务进度、错误、告警，并发起对账和修复。

这段按目标方案复现完成后讲；当前设计阶段把“实现了”改成“设计中采用”。不需要开场就背全部表名或 SQL。

### 3.2 为什么选择拉模式，由哪一方负责

**业务问题：**SAP 维护权威主数据，SRM 需要独立掌握消费进度和本地可用性。

**选择：**外围提供按修改时间筛选、按时间和 ID 排序的分页接口；SRM 定时调用，负责频率、限量、字段校验、转换、落库、检查点和失败恢复。SRM 不直接查询外围业务数据库。

**原因：**业务允许周期性更新，消费方可以按自己的处理能力推进；无需要求外围每次维护数据时都成功回调 SRM。拉取内容是接口筛出的增量，不是每次拉全量。

**口述：**

> 上游提供的是“数据能被查询出来”的能力，我在 SRM 做的是“如何可靠地消费并维护副本”。上游有接口不意味着消费端不用开发。拉取并不天然更一致，正确性来自双方明确的查询契约和本地事务、幂等、恢复、对账机制。

### 3.3 候选技术方案比较

这些技术不全处于同一层次：ID、时间和指纹参与变化识别；CDC 捕获变化；MQ 传输事件；它们可以组合，不能简单当作完全互斥的同类产品。

| 方案 | 如何工作 | 优点 | 本项目为何不单独采用 |
| --- | --- | --- | --- |
| 每次全量 | 每轮读取所有当前主数据 | 简单，小数据下可行 | 有重复传输；本项目希望练习增量和恢复，全量保留给初始化及对账 |
| 业务表自增 ID | id > lastId | 新增扫描简单 | 旧行修改、冻结、禁用时 ID 不变；自增分配也不代表提交顺序 |
| 只用修改时间 | updated_at > lastTime | 能识别旧行修改 | 时间非唯一，简单按最后时间继续会漏同时间后续行；还要处理精度与迟提交 |
| 修改时间＋ID | 按 (updated_at,id) 继续 | 同时支持修改筛选与同时间分页 | 需要可靠时间、固定窗口、回扫及对账；这是本次选择 |
| 对象版本号 | 对每行比较版本 | 适合判断对象新旧 | 本次不要求外围新增版本字段；每行版本也不自动提供全局消费位置 |
| 全量＋Hash 指纹 | 按业务键比内容指纹 | 不依赖修改时间也能发现当前内容差异 | 网络仍全量，哈希不能判断谁更新；保留作对账和重复内容判断 |
| 数据库日志 CDC | 从数据库变更日志捕获插入、修改、删除 | 适合低延迟变化流与删除捕获 | 需要日志权限、网络及连接器运维；当前接口消费边界没有这些接入条件 |
| 外围业务事件＋MQ | 外围维护业务时发布事件，SRM 消费 | 可解耦、削峰，适合多订阅方 | 外围须可靠产出事件，另需处理重复、顺序、积压及补偿；本期无此要求 |

**结论：**在“源表已有稳定自增 ID、可靠修改时间，接口支持筛选排序，业务接受周期性更新”的条件下，组合游标能以较少源端配合满足目标。它不是所有企业场景的最佳方案；如果外围没有可靠时间，就回退为分页全量＋指纹比较，或者协商其他标准增量能力。

### 3.4 为什么单独 ID 不够：举旧记录修改的例子

> 上次同步已经处理到 ID=100，但 ID=20 的成本中心今天被冻结。如果我只查 id>100，就永远看不到这次冻结。组合方案先按修改时间识别它的变化，再用 ID 做排序的第二关键字，所以 ID=20 一样会被同步。

这里的 ID 是源记录稳定身份，不是变更次数，不是本地单据 ID。

### 3.5 为什么单独时间戳不够：举同时间多条记录的例子

> 假设同一微秒有 800 行变化，每页只能取 500 行。第一轮读完后如果直接把条件改成 updated_at>最后时间，剩下 300 行就被跳过了。我保存的是最后一行的“时间＋ID”，下一页继续取时间更大，或者时间相同但 ID 更大的记录。

这不是说任何时间方案都无法解决同时间问题；引入稳定的第二排序键，就是补齐简单时间分页的缺陷。排序及比较始终先时间后 ID，不能写成“时间大于且 ID 也大于”。

### 3.6 为什么不用指纹作为主要增量依据

> 指纹适合判断已经拿到的内容有没有变化。但如果外围不支持变化筛选，我为了算指纹仍然得拉取所有行，它主要减少目标写入，减少不了全量网络传输。因此本方案用时间窗口筛变化，用组合游标翻页，用指纹判断内容和做对账，三者职责不同。

按业务键建索引或使用 Map 后逐条比对，不必进行两两比较，不能照搬学习笔记里“指纹比较必然是 N×N”的说法。指纹也不是版本号，不能仅凭两个不同哈希判断哪个状态更新。

### 3.7 为什么本期不选 CDC

> CDC 更适合需要准实时变更、源端允许开放日志订阅的场景。我们是通过外围接口消费小规模主数据，没有源库日志接入条件，也不要求还原每次中间变化，所以优先选择现有字段能支撑的接口增量，避免为了同步练习先建设一套源库日志链路。

不同数据库的 CDC 机制并不相同：PostgreSQL 的 Debezium 连接器使用逻辑解码及复制槽等能力，不应一概说成“伪装从库读取 MySQL binlog”。参见 [Debezium PostgreSQL 官方说明](https://debezium.io/documentation/reference/stable/connectors/postgresql.html)。CDC 是捕获方式，不会自动让 SRM 与源系统形成跨系统强一致事务。

### 3.8 为什么有 MQ 也不能直接解决源端增量问题

> MQ 能传递变化，但先要有人可靠识别并发布变化。外围如果没有事件接口，我们在 SRM 放一个消息队列，并不能知道源表哪行变了。即使外围能发事件，还需要考虑数据库更新成功但消息没发出去、重复投递、顺序、消费者失败等问题。本期周期性主数据同步不依赖这条链路，把它留到后续独立练习。

消息确认和消费确认负责各自链路的可靠性，重传仍可能产生重复；不能把“用了 MQ”说成天然不丢不重。参见 [RabbitMQ 可靠性说明](https://www.rabbitmq.com/docs/reliability)。

如果未来要求秒级生效、多系统订阅或完整变更历史，可以重新评估外围标准事件、CDC＋MQ 等路线，而不是因为当前未采用就否定它们。

## 4. 组合游标的完整实现讲解

### 4.1 源端只保留一张主数据表

模拟源统一使用 sap_master_data 一张表，以 entity_type 区分成本中心和汇率，包含：

| 字段 | 用途 |
| --- | --- |
| id | 源表自增主键，稳定、不复用 |
| entity_type、business_key | 类型与业务唯一身份 |
| payload | 类型对应的业务内容 |
| blocked、enabled、is_deleted | 冻结、启用、逻辑删除状态 |
| created_at、updated_at | 创建时间与每次业务变化的修改时间 |

不增加 source_version，不增加流时钟、变更事件、物化快照表。数据库 identity sequence 和索引属于表基础设施，不是另外维护的事件表。真实外围如何存储由其系统决定，这张统一表是模拟器模型，不声称 SAP 原本如此建表。

每次业务字段或状态改变，都必须与 updated_at 在同一个源事务里保存。时间使用数据库生成值，同一行每次变更严格增加，保留微秒精度；更新完成后返回数据库实际保存值。已有可靠修改时间是选择该方案的前提，不是 SRM 能单方保证的能力。

### 4.2 首次全量：按 ID 上界扫描，再补期间变化

**问题：**本地首次没有副本，需要建立基线；全量期间外围也可能继续变化。

**方案：**

1. 读取源端时间 T0 和该类型当前可见最大 ID=M，保存到 SRM 检查点。
2. 按 id>lastId 且 id<=M 升序分页，不把全部源数据加载到内存。
3. 每页读取当时的最新内容，不用 updated_at<T0 把扫描期间修改过的旧行排除。
4. 扫描完成后将完整水位初始化为 T0，再从 T0 前的重叠范围接续时间增量。

**口述：**

> 固定 ID 上界让首次扫描范围有限，初始化和增量之间用 T0 接续。全量期间新增或修改的数据，后续按更新时间再次捕获，已经同步过的状态由幂等写入处理。这里没有源端快照，因此多页读取不是同一时刻的全库镜像。

扫描 ID 有空洞也正常；不能用 lastId/M 伪造精确完成百分比。未提交小 ID 的极晚提交仍受时间迟延契约和后续对账约束。

### 4.3 固定时间窗口：让每一轮有明确结束点

| 符号 | 含义 |
| --- | --- |
| W | 上次完整完成的窗口上界 |
| L | 安全延迟，初值 120 秒 |
| R | 重叠回扫长度，初值 300 秒 |
| S | 本轮下界 max(epoch,W-R) |
| E | 本轮上界 sourceNow-L |
| C=(t,id) | 本轮最后成功页的位置 |

**口述：**

> 我不会一边翻页一边不断追当前时间，而是在新一轮开始时固定区间 [S,E)。E 使用源端数据库时间减去安全延迟，S 从上次完整水位向前回扫一段。这样本轮查询范围固定，最新变化留给后续窗口，边界附近的数据也有机会再次被读取。

L/R 是初始工程参数，不是经过压测或源端测量确定的值。源时间倒退超过约定容差时暂停并告警，不能通过降低水位掩盖源时钟问题。

### 4.4 组合游标分页 SQL

下列 SQL 由源端查询接口内部执行，SRM 通过 HTTP 传筛选参数，不直接查询 SAP 库。

~~~sql
SELECT id, business_key, payload, blocked, enabled, is_deleted, updated_at
FROM sap_master_data
WHERE entity_type = :entityType
  AND updated_at >= :windowStart
  AND updated_at < :windowEnd
  AND (
       updated_at > :lastTime
       OR (updated_at = :lastTime AND id > :lastId)
  )
ORDER BY updated_at ASC, id ASC
LIMIT :pageSize;
~~~

第一页不带最后时间/ID条件；后续页使用最后返回行的二元位置。PostgreSQL 可以将组合条件写为 (updated_at,id)>(:lastTime,:lastId)。

**需要强调：**“组合游标”是分页键，不是要求把源表主键改成时间＋ID的联合主键。源表主键仍然只有自增 id；源端可增加 (entity_type,updated_at,id) 查询索引。

源记录 ID 在 JSON 中按字符串传输，避免浏览器大整数失真；时间保留服务端原始微秒值，不能经前端 Date 转换后截断为毫秒再作为游标回传。

### 4.5 完整水位和页游标分开保存

**问题：**处理完某一页，不等于整个时间窗口已经完成。

**方案：**检查点同时保存 W、活动窗口 S/E，以及页游标 C。每个成功页只推进 C；最后一页（包括空尾页）事务成功后才将 W 更新为 E，并清空活动窗口。

**口述：**

> 例如上次完整完成到 10:00，本轮计划处理到 10:08，现在某页已经读到 10:03。此时页游标可以是 10:03 的某个 ID，但完整水位仍然是 10:00。只有剩余页都成功，才能把完整水位推进到 10:08，不能提前跳过尚未处理的数据。

没有变化时也推进到 E，不把最后记录时间当作整轮完成上界。失败恢复优先使用已保存活动窗口，不重新计算上界。

### 4.6 安全延迟、重叠回扫分别解决什么

**安全延迟：**避开刚赋修改时间但可能尚未提交、或尚未复制到查询节点的变化。

**重叠回扫：**下一轮从 W-R 开始，重复检查边界附近的记录；重复读取由幂等处理。

**组合游标：**解决窗口内相同修改时间下的排序和分页，不负责判断数据库事务是否提交。

**口述：**

> 我没有把组合游标当成万能防漏机制。它解决相同时间的翻页；延迟窗口和回扫处理约定范围内的可见性迟延；超出约定的长事务、不维护修改时间等异常，再通过全量对账兜底。

任意迟提交无法由有限 R 无条件覆盖。源行的更新时间严格增加也不等于它就是提交时间。失联很久后可从原窗口下界重扫，仍不改变这个边界。

### 4.7 分批读取和批量写入

默认源页 500 行，目标每条参数化多 VALUES Upsert 最多 200 行；一页拆出的 200＋200＋100 三条 SQL 放进同一个页事务。

分页控制网络返回量和内存，批量写控制数据库往返次数，不能把源端一次返回全表、SRM 再切 List 说成解决了源端分页。

同一实体顺序翻页，不让多个线程无序推进同一个页游标；成本中心与汇率可以按不同数据集并行。

### 4.8 页级事务与断点恢复

~~~text
事务外：HTTP 取本页 → 解析、校验和字段转换
事务内：执行权校验 → 批量 Upsert → 成功页审计/统计 → 检查点
COMMIT：上述目标数据和进度共同生效
~~~

**口述：**

> 第三页如果在第二条 SQL 失败，这一页所有业务写入和进度一起回滚，前两页不回滚。重新执行时先读数据库里最后成功的组合游标，再拉后续数据。所以既不会先推进游标导致丢数据，也不会为了一个失败页撤销整个同步任务。

HTTP 在数据库事务之外；目标业务数据和检查点在同一个本地事务内。不是“业务写入和游标各自独立提交”。提交结果不确定时重新读取持久化进度；最后页同时保存窗口完成标记，避免进程退出后把已完成窗口误当未完成。

### 4.9 幂等与新旧数据保护

| 目标状态 | 普通同步行为 |
| --- | --- |
| 目标不存在且业务键无冲突 | 新增 |
| 源 updated_at 大于目标 source_updated_at | 更新业务内容、状态、时间和指纹 |
| 时间相同且实际内容相同 | 忽略重复读取 |
| 时间相同但内容不同 | 整页失败并告警，进入对账核查 |
| 源时间更早 | 忽略旧响应，不覆盖较新状态 |
| 源 ID 和业务唯一键映射冲突 | 阻断，不任意合并 |

数据库对 source_system＋source_id 设置唯一约束，同时校验成本中心控制范围＋编码、汇率类型＋币种对＋生效日等业务唯一性。指纹从规范化实际字段计算，不拿本地主键、同步时间等技术字段参与。

**口述：**

> 唯一键保证重复拉取不会变成重复业务行，源修改时间保证旧状态不覆盖新状态，指纹区分同一时间内容是否一致。三者分工明确。读取是可重试的，目标写入做到幂等，不把它称作跨系统 exactly-once。

### 4.10 修改、冻结、禁用和删除如何同步

| 操作 | 源端变化 | SRM 处理 |
| --- | --- | --- |
| 修改旧记录 | 同 ID，更新业务内容和 updated_at | 增量更新原目标行 |
| 冻结/解冻 | blocked 变化并更新时间 | 保留记录，业务按冻结状态判断可用性 |
| 禁用/启用 | enabled 变化并更新时间 | 保留历史引用，控制新业务可用性 |
| 逻辑删除/恢复 | is_deleted 变化并更新时间 | 同步墓碑或恢复状态，不物理删历史引用 |
| 有效期自然到期 | 可能没有数据库更新 | 本地按业务日期校验，不等待“到期事件” |
| 同日汇率修订 | 同源 ID和业务键，时间增加 | 更新同一主数据，不重算历史单据快照 |
| 越权物理删除 | 源行彻底不存在 | 时间增量无法感知，由全量对账发现并复核 |

源接口不能过滤掉冻结、禁用或逻辑删除行，否则 SRM 无法知道它们变成不可用。三个状态相互独立，解冻不自动启用，启用不自动撤销逻辑删除。

同一源行在两次读取之间“冻结→解冻”，SRM 可能只看到最终解冻状态；当前需求是最新状态副本，不是变更历史审计。

### 4.11 全量对账与差异修复

**问题：**增量无法覆盖本地误删、字段被误改、源端未维护时间、异常长事务和物理删除等全部情形。

**对账：**独立运行 RECONCILE，按源 ID 上界分页扫当前主数据，在 SRM 记录本次见到的源 ID；比较目标实际字段重算的指纹。只有完整扫描结束，才判断本次范围内哪些目标行在源端未出现。差异通过源端单行查询再次复核。

**修复：**REPAIR 使用最新源行复核，不拿旧报告 payload 直接覆盖；允许补齐目标、更新较旧值、授权修复等时间不同内容；不自动覆盖时间较新的目标，不自动删除源端缺失的本地行。目标写入、修复结果和修复扫描进度同事务提交。

**口述：**

> 对账不是再跑一遍增量，它会绕开时间筛选扫描当前数据，所以能发现时间契约之外的问题。由于没有源端快照，我只把扫描结果当作观察值，差异再点查确认；不宣称多页读取是同一时点镜像。对账和修复使用自己的扫描进度，不修改普通同步的完整水位。

源端缺失要在权限有效的查询中复核，网络超时不能当作不存在。对账中断时不输出完整缺失结论；新补偿运行可以重新全扫，简化不完整观察集的正确性。

### 4.12 错误、告警及可视化

每次运行保留来源、状态、窗口、组合游标、成功页、读取/应用/忽略数、错误原因、尝试次数及下次重试时间。失败页事务回滚后另行记录失败；目标库完全不可用时先由应用日志留痕，不承诺数据库错误一定已经入库。

告警包含连续失败、滞后、源时间回退、同时间内容冲突、身份冲突和对账差异，按任务＋类别去重。确认已读不等于已解决，修复仍有剩余差异时不能把所有告警清空。

前端展示完整水位和当前页进度，提供触发、取消、补偿、对账及修复入口。滞后要结合 sourceNow-L-W 判断，不能仅凭“最近任务执行成功”认定已经追上。没有接入的邮件、短信或指标平台不写入完成项。

## 5. 第二条的口述：调度计划与任务可靠执行

### 5.1 一分钟开场

> 同步引擎回答的是“数据如何处理”，调度部分解决“何时执行、由谁执行以及失败后谁恢复”。我使用 XXL-JOB 管理 Cron 和执行器路由，业务侧保留持久化运行记录，并将成本中心和汇率分别注册为 Handler。
>
> 定时触发、人工触发以及对账修复会共用对应数据集的租约。实例领取时获得递增 token，执行期间心跳续租，每个页事务提交前校验 owner、token 和有效期，防止旧实例恢复后继续写入。
>
> 重试明确只有一个负责人：XXL 来源交给 XXL 重试，人工来源使用本地持久化退避；后续执行读取已经提交的窗口和组合游标恢复。结合请求幂等、人工补偿、日志与页面，可以追踪每一次任务的业务结果。

### 5.2 为什么接入 XXL-JOB，而不只用 @Scheduled

| 方案 | 优点 | 本项目的取舍 |
| --- | --- | --- |
| @Scheduled | 简单、少组件 | 单机维护任务够用，多实例和集中运维需补充能力 |
| Quartz | 适合较复杂触发规则，可配置集群 | 当前主要是按 Cron 调用已有业务 Handler，暂不需要更复杂日历规则 |
| XXL-JOB | 集中配置计划、执行器路由、日志及重试 | 选择接入，业务侧仍负责数据执行权和检查点 |

> 成本中心和汇率频率不同，运维需要查看计划、执行日志并手动触发，所以我接入已有调度平台，不自己再造调度中心。@Scheduled 仍可用于本地心跳、失联扫描和人工任务领取，这不等于维护两套业务 Cron。

XXL 的节点路由不能代替所有业务入口的互斥，也不能天然保证任务只执行一次。

### 5.3 调度中心和 SRM 如何分工

~~~text
Admin 按计划触发 Handler
  → 提取调度身份并幂等创建/复用 job_run
  → 检查业务开关，取得数据集租约
  → 读取检查点中的首次扫描进度或固定窗口/组合游标
  → 分页执行并提交数据和进度
  → 保存业务终态
  → Handler 向 Admin 反馈业务成功或失败
~~~

Handler 等业务执行完成再回报，不是只投进本地队列就报成功。调度日志中的业务 runId 和 SRM 保存的 XXL 任务信息双向关联。调度库与业务库之间没有分布式事务，依靠执行身份、幂等和业务状态协调。

### 5.4 请求幂等：区别重复请求与新一轮任务

人工调用携带 Idempotency-Key，相同 key 和相同请求复用原运行；不同任务/模式/参数使用同 key 返回冲突。新的调度轮次使用新身份，不把所有调用都当作重复。

XXL 回调按任务 ID、日志身份摘要和分片信息建立稳定执行身份；同一次重复回调不重复建业务运行。人工补偿创建新 run，并用 parent_run_id 关联原失败运行，不能更改失败历史来伪装从未失败。

请求幂等已增加参数指纹校验，覆盖任务、模式、原因、来源和补偿父运行；本轮尚未执行验证。

### 5.5 数据集租约与 fencing token

同一数据集的 AUTO、RECONCILE、REPAIR，无论来自人工还是 XXL，都使用同一 resource_key。通过 PostgreSQL 条件更新领取过期租约，设置 owner、lease_until 并递增 token；初值 60 秒租约、15 秒心跳。

> A 暂停失去租约后，B 取得新的 token。A 即使恢复，也必须在页事务里重新验证 owner 和 token，验证失败就不能写数据或推进组合游标。仅靠“锁当时拿到过”不够，提交前还要确认仍拥有执行权。

固定锁序为运行行→租约行→检查点和业务数据。HTTP 在事务外。令牌保护的是本地提交权限，不能撤回已发出的 HTTP 请求；源查询是读接口，允许安全重读。

### 5.6 重试、补偿和长期中断

| 来源/情况 | 处理 |
| --- | --- |
| 人工/本地任务的可重试故障 | RETRY_WAIT，持久化 next_retry_at，基础退避 30/60/120/240 秒＋抖动，最多 5 次 |
| XXL 来源执行失败 | SRM 保存失败并向 Admin 返回失败，由 XXL 配置后续重试，不进入第二套本地重试队列 |
| 契约错误、权限错误、身份冲突等 | 失败并告警，修复原因后人工重试，不无条件反复请求 |
| 本地失联任务 | 检查租约和 token 后回收，按重试归属进入待重试或失败 |
| 失败/取消后的人工补偿 | 新建关联 run，AUTO 读取现有检查点；对账可重新扫描生成新报告 |

恢复保持原活动窗口 S/E，使用最后提交的组合游标 C；超过约定中断时长可从原 S 回扫整个未完成窗口，W 不前移。延迟超过回扫能覆盖的范围，仍由全量对账补齐。

本地退避、XXL 重试不能同时负责同一个运行。底层数据库异常需要区分暂态故障与永久约束错误，该精细分类是目标方案要求，不将旧代码的粗粒度分类当作已完成。

### 5.7 状态机、取消与开关

状态包括 PENDING、RUNNING、RETRY_WAIT、CANCEL_REQUESTED、CANCELLED、FAILED、SUCCEEDED，持久化保存，不仅依赖内存线程。

运行中取消先请求，安全页边界检测后停止；已提交页保留，正在外部等待的请求可能需要超时后才能结束。关闭 SRM 业务开关阻止新执行，取消已有任务是另一操作；XXL Cron 启停由 Admin 管理。

同实体顺序处理，不同数据集可并行。本地人工任务路径可用有界并发及信号量控制领取，不能把它包装成所有入口共享的全局限流器或已经通过压测的高并发能力。

### 5.8 日志追踪与告警

SRM 记录业务 runId、调度来源、XXL 任务 ID、执行节点、窗口、页结果和失败原因，Admin 负责调度日志。两边可以关联定位同一次运行。

页面支持运行追踪、错误查看、取消、补偿和告警确认。连续失败、同步滞后及对账差异按各自条件恢复，不因一次“空任务成功”直接宣称所有问题已经修好。

## 6. 用一个失败案例串起两条简历功能

> 财务把 ID=20 的成本中心冻结，源表同一行更新时间增加。XXL 到点触发，SRM 拿到租约，按固定时间窗口和组合游标拉取，所以即使这个 ID 比历史最大 ID 小，也能读到这次修改。
>
> 假设前两页成功，第三页遇到接口 503，第三页没有推进检查点。XXL 来源由平台重试，人工来源进入本地退避。恢复实例取得新 token，读取原窗口和最后成功页的时间＋ID继续执行；重复记录由业务唯一键和源修改时间保护处理。
>
> 如果本地之前有人误删了另一条记录，日常增量未必会再次返回它，独立全量对账会发现缺失，再由显式修复补齐。页面可以看到失败、恢复及修复过程。

数据同步讲“如何取数和正确提交”，调度讲“谁触发、谁有权提交、谁负责再次执行”，两条都能独立展开。

## 7. 高频追问及回答要点

| 追问 | 回答要点 |
| --- | --- |
| 最后到底选的是 ID 还是时间？ | 变化筛选主要依赖时间，分页键为时间＋ID；ID 是同时间的第二排序键 |
| 是否改成联合主键？ | 不改，源表主键还是 ID，组合游标是查询排序/分页概念 |
| 为什么不是单独 ID？ | 旧 ID 修改、冻结、禁用不会生成新 ID |
| 为什么不只用时间？ | 简单“大于最后时间”的分页会跳过同时间剩余行，ID 使排序唯一 |
| 有没有用指纹？ | 用于内容比较和对账，未把全量算指纹当作源端增量过滤 |
| 指纹比较一定 N² 吗？ | 不一定，按键索引/Map 可逐行比较；主要成本是全量读取和传输 |
| 有组合游标是不是绝不会漏？ | 不是，还依赖可靠时间、迟延契约、回扫和全量对账 |
| 什么情况下选 CDC/MQ？ | 对准实时、多消费者、删除事件或历史变化要求更高，且源端权限及事件链路允许时 |
| 为何增量还要全量对账？ | 发现增量链路外的误删、改数、时间契约异常和物理删除 |
| 源端只有一张表，能看到每次冻结吗？ | 不能，只保证最终状态收敛；完整事件历史需其他捕获能力 |
| 上游做了筛选，SRM 还有多少工作？ | 编排、调用、校验、转换、批量入库、进度、幂等、重试、告警、对账和修复 |
| 先写数据还是先存游标？ | 同一本地事务共同提交，不拆开；请求源端在事务外 |
| 有唯一键为什么还要比较时间？ | 唯一键防重复行，时间保护防旧内容覆盖新状态 |
| 为何有 XXL 还要租约？ | 还有人工和修复入口，需要统一控制同数据集执行权 |
| 为什么还有 token？ | 防止失去租约的旧实例恢复后继续写入 |
| 系统宕机错过几个 Cron 怎么办？ | 后续从持久化水位覆盖未处理范围，不依赖每个 Cron 都准时触发 |
| 这是高并发模块吗？ | 重点是同步可靠性和多实例协调，不声称有未经测量的吞吐与并发数据 |

## 8. 学习文档中的几处说法如何用于面试

用户提供的《数据同步技术实现方案》用于了解候选技术，不将其中的简化示例逐句照搬为本项目结论：

1. 业务自增 ID、对象版本号、全局变更位置是不同概念；本次只要求源业务表有稳定 ID 和可靠时间。
2. 指纹对比不是天然 N×N，也不天然减少网络全量读取。
3. CDC 不等于 MQ，也不等于跨系统强一致；两者可以组成链路。
4. 数据和检查点必须在同一页事务提交，不采用参考伪代码中的各自独立提交。
5. 全量覆盖不能自动识别物理删除；仍需完整性检查和缺失复核。
6. 本项目主数据和任务状态使用 PostgreSQL，不因参考材料有 MySQL 示例就改口为 MySQL；XXL Admin 自己的调度库是另一职责。
7. XXL 不天然保证恰好一次业务执行；仍需要请求幂等、数据幂等和执行权检查。
8. 对象已停用和物理删除不是一回事，接口必须返回不可用行才能同步它们的状态。
