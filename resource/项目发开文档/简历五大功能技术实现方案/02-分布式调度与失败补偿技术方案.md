# XXL-JOB分布式调度与失败补偿技术方案

> 日期：2026-10-17。性质：已确认设计，待编码复现。
> 目标：使用XXL-JOB统一管理SRM集成任务的Cron、启停、路由、超时、重试和调度日志，并由SRM业务任务库保障幂等、断点恢复、租约隔离和数据一致性。
> 技术基线：Java 17、Spring Boot 3.0.7、XXL-JOB 2.4.2、PostgreSQL 16、MySQL 8、Vue 3。
> 实施约束：不自动执行测试、联调或压测；需要验证时先征得用户批准。
> 当前进度：01主数据同步和数据库任务底座已经实现；本方案将原Spring Cron触发层替换为XXL-JOB，保留并增强SRM业务补偿层。

## 1. 客户需求与业务场景

集团SRM需要按计划从SAP同步成本中心和汇率。SRM部署多个实例后，如果每个实例都使用普通`@Scheduled`，同一个Cron时刻会被重复触发，造成重复调用SAP、游标竞争和重复告警。

客户还要求：

- 运维人员可以在统一控制台修改Cron、暂停、恢复和手工触发任务；
- 一个执行节点宕机后，调度可以切换到其他健康节点；
- 网络故障可以自动重试，失败后可以人工补偿；
- 重试不能从头重复全量处理，必须从SRM最后成功检查点继续；
- 旧节点租约失效后即使恢复，也不能覆盖新节点写入的数据和游标；
- 业务人员能在SRM页面查看真实的拉取、应用、忽略、差异和失败页信息。

因此，本功能不是“接入XXL-JOB后删除本地任务表”，而是采用两层治理：

```text
XXL-JOB调度层
  ├─ Cron、启停、人工触发、路由、超时、重试、调度日志
  └─ 选择一个可用SRM执行器
                    ↓
SRM业务执行层
  ├─ 业务运行记录、请求幂等、资源租约、fencing token
  ├─ SAP分页拉取、批量幂等落库、检查点提交
  └─ 页级回滚、断点恢复、对账、业务告警和人工补偿
```

XXL-JOB解决“何时调度、由谁执行”，SRM解决“如何正确执行以及从哪里恢复”。

## 2. 版本选择

当前项目使用Spring Boot 3.0.7。XXL-JOB 3.5.0于2026年10月发布，其工程基线已经升级到Spring Boot 4.1和Spring 7；直接把3.5.0执行器核心嵌入当前项目，会扩大Spring、Netty等依赖兼容风险。

首期固定使用XXL-JOB 2.4.2：

- 功能已覆盖Cron、路由、故障转移、阻塞策略、超时、失败重试、日志和告警；
- 执行器核心仍使用稳定的Netty 4.1体系，与当前项目技术代际更接近；
- 调度中心作为独立Docker容器运行，不把其Spring Boot 2.7依赖带入SRM应用；
- `xxl-job-core`只由`integration-service`模块引入，聚合服务通过模块依赖复用；
- 后续若项目整体升级Spring Boot，再单独评估XXL-JOB升级，不在本功能中顺带升级全项目。

版本依据：[XXL-JOB 2.4.2官方文档](https://github.com/xuxueli/xxl-job/blob/2.4.2/doc/XXL-JOB%E5%AE%98%E6%96%B9%E6%A1%A3.md)、[XXL-JOB发布页](https://github.com/xuxueli/xxl-job/releases)。

## 3. 部署拓扑

### 3.1 开发聚合模式

```text
Vue 5173 → Gateway 8080 → Aggregation Service 8090
                              ├─ integration模块
                              └─ XXL-JOB Executor 9999

XXL-JOB Admin 9090 → Executor 9999
       ↓
XXL-JOB专用MySQL 3307

Aggregation Service → PostgreSQL 5433/integration_schema
```

开发人员只手动启动`api-gateway`和`aggregation-service`。MySQL、XXL-JOB Admin与其他中间件由Docker Compose启动。独立`integration-service`不同时启动，避免重复注册和执行器端口冲突。

Windows宿主机运行执行器、Admin运行在Docker时，开发配置通过`xxl.job.executor.address`注册Docker可访问的`host.docker.internal:9999`。生产环境通过环境变量配置容器服务地址，不硬编码本机地址。

### 3.2 线上微服务模式

```text
Gateway → integration-service实例A ┐
                                    ├─ 相同AppName注册到XXL-JOB
        → integration-service实例B ┘

XXL-JOB Admin集群 → 独立MySQL主库
```

线上不启动聚合服务。多个`integration-service`实例注册同一个AppName，XXL-JOB按路由策略选择一个实例。每个实例可使用相同容器内执行器端口；宿主机映射和注册地址由部署环境提供。

## 4. 数据库边界

XXL-JOB Admin官方表使用MySQL语法，因此增加独立MySQL实例，仅保存调度元数据、执行器注册信息和调度日志。它不保存成本中心、汇率和SRM游标。

| 数据库 | 数据范围 | 是否允许跨库事务 |
| --- | --- | --- |
| MySQL `xxl_job` | Cron、路由、调度日志、执行器注册、Admin用户 | 否 |
| PostgreSQL `integration_schema` | `job_run`、请求幂等、资源租约、同步检查点、失败页、告警 | 否 |

两个数据库之间不做分布式事务。XXL-JOB可能在网络边界上重复触发。2.4.2执行上下文公开`jobId`、日志文件名和分片信息，但不直接公开`logId`；因此SRM使用`job_id + SHA-256(job_log_file_name) + shard_index + job_code`构造幂等键。数据库只保存日志文件名摘要，不保存执行器本地绝对路径。

## 5. 任务清单和控制台配置

首期只接入当前已经实现的两个主数据任务：

| 任务名称 | JobHandler | Cron | 路由策略 | 阻塞策略 | 过期策略 | 超时 | 失败重试 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| SAP成本中心增量同步 | `sapCostCenterSyncJobHandler` | `0 */10 * * * ?` | 故障转移 | 单机串行 | 忽略 | 30分钟 | 2次 |
| SAP汇率增量同步 | `sapExchangeRateSyncJobHandler` | `0 10 2 * * ?` | 故障转移 | 单机串行 | 立即执行一次 | 15分钟 | 2次 |

时区统一为`Asia/Shanghai`。开发时Cron是演示参数，生产频率由业务SLA决定。

成本中心和汇率都使用单实例路由，不使用“分片广播”。原因是当前SAP接口提供的是全局有序游标；如果直接按执行器数量分片，每个分片没有独立游标边界，容易重复或遗漏。后续只有当源接口明确提供稳定分区键和分区游标时，才增加分片并行。

周度全量对账在主数据任务稳定后注册为独立Handler；验收补偿和BPA恢复分别在04、03功能完成后再注册，不在第二功能中伪造尚不存在的业务处理器。

## 6. 执行器接入

`integration-service`增加条件化XXL-JOB配置：

```yaml
xxl:
  job:
    enabled: ${XXL_JOB_ENABLED:false}
    admin-addresses: ${XXL_JOB_ADMIN_ADDRESSES:http://localhost:9090/xxl-job-admin}
    access-token: ${XXL_JOB_ACCESS_TOKEN:}
    executor:
      app-name: procurement-integration-executor
      address: ${XXL_JOB_EXECUTOR_ADDRESS:}
      ip: ${XXL_JOB_EXECUTOR_IP:}
      port: ${XXL_JOB_EXECUTOR_PORT:9999}
      log-path: ${XXL_JOB_LOG_PATH:./logs/xxl-job}
      retention-days: 30
```

生产环境必须设置非空Token，Admin管理页面不直接暴露公网。开发环境也通过`.env`注入Token，不把真实凭证提交到仓库。

两个Bean Handler不复制同步逻辑，只将XXL上下文转换为统一任务命令：

```java
@XxlJob("sapCostCenterSyncJobHandler")
public void costCenter() {
    coordinator.executeFromXxl("SAP_COST_CENTER_DELTA");
}
```

业务执行统一下沉到`JobExecutionCoordinator`，人工任务和XXL任务复用同一个`MasterDataSyncService`、资源租约和错误分类。

## 7. XXL调度与业务运行的映射

一次XXL调度会在PostgreSQL创建或复用一条`job_run`：

```text
XXL触发
  → 读取jobId、jobLogFileName、分片序号
  → logKey = SHA-256(jobLogFileName)
  → requestId = xxl:{jobCode}:{jobId}:{logKey}:{shardIndex}
  → 幂等创建job_run
  → 精确领取该run并获取resourceKey租约
  → 同步分页执行
  → 更新业务终态
  → 将成功/失败同步返回XXL-JOB
```

XXL Handler必须等待本次业务运行进入终态后再返回，不能“提交到本地线程池后立即返回成功”，否则Admin会把仅仅进入队列误判为业务同步成功。

人工触发仍通过SRM接口异步创建`MANUAL`运行，由本地受限线程池执行。这样SRM页面不依赖Admin登录态；XXL控制台的人工触发则走XXL Handler。两种入口最终竞争同一个`resourceKey`租约，不能同时写同一数据集。

XXL入口不得沿用现有“发现同模式活动任务就映射到同一run”的人工提交语义。相同XXL幂等键可以返回原run；不同XXL调度若发现资源忙，则为本次调度记录`JOB_BUSY`失败并返回XXL失败，由调度中心稍后重试。这样一个XXL线程不会错误等待或接管另一个入口创建的业务运行。

## 8. 资源租约和fencing token

XXL-JOB保证一次计划调度只选择一个执行器，但不能完全消除以下场景：

- Admin没有收到回调，重新触发任务；
- 执行器长时间GC或网络隔离，故障转移到另一实例；
- 人工触发与计划任务同时到达；
- 成本中心增量与成本中心修复任务同时写同一数据集。

因此保留PostgreSQL业务租约，并将租约键从`jobCode`提升为数据集资源：

| jobCode/模式 | resourceKey |
| --- | --- |
| 成本中心增量、对账修复 | `SAP_COST_CENTER_WRITER` |
| 汇率增量、对账修复 | `SAP_EXCHANGE_RATE_WRITER` |

领取租约时递增`fence_token`。每一页写入事务按“run行 → lease行 → 业务数据/检查点”的顺序加锁并校验owner、token和有效期。旧实例租约失效后，即使线程恢复，也不能写业务数据、推进检查点或覆盖新实例终态。

XXL-JOB的“单机串行”只约束同一执行器内部，PostgreSQL租约负责跨实例和跨入口互斥，两者职责不同。

## 9. 失败、重试和断点恢复

### 9.1 XXL任务

XXL任务执行失败时：

1. 当前页事务回滚，已完成页和检查点保持提交；
2. `job_run`记录错误码、脱敏摘要、失败页和执行节点；
3. Handler向XXL-JOB返回失败；
4. XXL-JOB按配置重试或由运维人工重跑；
5. 新执行从PostgreSQL最后成功检查点继续。

XXL触发的运行不再进入本地`RETRY_WAIT`，避免XXL和SRM两套自动重试同时工作。每次XXL重试对应新的调度日志；业务层通过检查点保证重复执行安全。

### 9.2 SRM人工任务

SRM页面创建的人工任务继续使用本地持久化退避：30秒、60秒、120秒、240秒，上限5分钟并加入20%抖动。退避使用`next_retry_at`，不占用线程睡眠。

### 9.3 错误分类

| 错误 | 处理 |
| --- | --- |
| 网络超时、SAP 429/5xx | 记录可重试错误；XXL任务返回失败，人工任务进入`RETRY_WAIT` |
| SAP认证或权限失败 | 立即失败并告警，修复配置后人工重跑 |
| 源字段缺失、业务键非法 | 失败页保留，不推进检查点 |
| 数据库连接失败 | 当前页回滚，允许重试 |
| 租约丢失 | 旧实例停止发起新请求和写入，由新实例接管 |
| 源游标过期 | 停止增量重试，进入基线重建审批流程 |

## 10. 数据模型变更

不修改已经执行过的`V2__job_scheduler.sql`，新增`V3__xxl_job_scheduler.sql`：

```sql
alter table integration_schema.job_definition
  add column handler_code varchar(100),
  add column resource_key varchar(100);

alter table integration_schema.job_run
  add column xxl_job_id bigint,
  add column xxl_log_key varchar(64),
  add column xxl_shard_index int,
  add column xxl_shard_total int,
  add column executor_address varchar(255);

create unique index uk_job_run_xxl_log_shard
  on integration_schema.job_run(job_code, xxl_job_id, xxl_log_key, xxl_shard_index)
  where xxl_log_key is not null;
```

迁移同时回填两个现有任务的`handler_code`和`resource_key`，插入两个资源租约行。原来按jobCode创建的租约行暂时保留以兼容历史记录，不在迁移中破坏性删除。

`job_request_key`继续保留。删除运行历史时必须先处理其请求键、页审计、失败页、对账差异和告警引用，不能绕过外键约束直接删`job_run`。

## 11. 线程、超时和取消

- XXL任务在XXL工作线程同步执行，业务代码不再次异步提交；
- SRM人工任务使用固定2线程、有限队列，禁止无界创建线程；
- SAP连接超时3秒、读取超时15秒；每页写入保持短事务；
- XXL任务超时是最后一道保护，业务循环每页检查线程中断和租约状态；
- 取消只在安全页边界生效，不强行中断正在提交的数据库事务；
- Handler结束前释放租约必须匹配owner和token，旧实例不能释放新实例的租约。

| 页面 | 展示内容 |

- 显示XXL-JOB是否启用、Admin地址、执行器AppName；
- 显示任务对应的Handler、XXL任务ID、日志键摘要、执行节点、分片参数；

- 不在SRM前端保存或代理Admin密码；
- 不使用iframe嵌入Admin，避免登录态、CSP和点击劫持问题。

## 13. 配置与启动

Docker Compose新增：

- `xxl-job-mysql`：MySQL 8，开发端口3307；
- `xxl-job-admin`：XXL-JOB 2.4.2，开发端口9090；
- 独立数据卷`xxl_job_mysql_data`；
- `deploy/xxl-job/init/01-tables_xxl_job.sql`固定保存2.4.2官方初始化SQL；
- `deploy/xxl-job/init/02-procurement_jobs.sql`幂等初始化执行器组和两个BEAN任务，避免每次搭建环境都手工录入；
- 两个种子任务只创建定义，初始`trigger_status=0`。执行器首次注册成功后由开发人员在Admin确认配置并启用；不在SQL中猜测`trigger_next_time`，避免新环境启动时误触发或产生错误的过期补偿；
- 初始化脚本仅在MySQL数据卷首次创建时执行，存量环境通过控制台或显式迁移更新；
- 健康检查，Admin等待MySQL健康后启动。

MySQL、Admin容器和Java进程统一设置`Asia/Shanghai`时区，避免控制台Cron、数据库时间和SRM运行记录出现时区偏差。种子任务使用固定AppName和Handler名称；密码、Token和环境相关地址仍由环境变量提供，不写死在SQL中。

开发模式：

```text
docker compose启动基础设施
→ 启动aggregation-service（注册XXL执行器）
→ 启动api-gateway
→ 启动Vue
→ 首次搭建时在Admin确认执行器在线并启用两个种子任务
```

线上微服务模式：

```text
启动XXL-JOB Admin集群和MySQL
→ 启动integration-service集群（注册相同AppName）
→ 网关继续按原路径转发业务API
```

前端始终请求同源`/api`，不会因为聚合模式和微服务模式切换而修改接口地址。

## 14. 安全设计

- Admin和执行器配置相同AccessToken；
- Admin仅开放到内网或VPN，不对公网暴露；
- 修改默认管理员密码，生产账号按执行器授权；
- `.env.example`只放示例值，真实Token和MySQL密码通过环境变量注入；
- Rolling Log不得打印SAP密钥、完整请求报文或个人敏感数据；
- GLUE在线脚本不用于本项目，任务均采用代码发布的BEAN模式；
- 生产环境限制Admin到执行器端口的网络访问范围。

## 16. 验收计划

以下操作只有获得用户测试批准后才执行：

| 场景 | 预期结果 |
| --- | --- |
| Admin按Cron触发成本中心任务 | 只生成一个业务运行并完成同步 |
| 两个执行器实例注册同一AppName | 故障转移策略只选择一个健康实例 |
| 人工触发与XXL任务同时到达 | 只有一个获得资源租约，另一个不并发写入 |
| 第三页网络失败后XXL重试 | 从最后成功检查点继续，不从第一页重跑 |
| 节点A租约过期、节点B接管、A恢复 | A不能写业务数据、游标或覆盖终态 |
| Admin暂时不可用 | 已运行任务继续完成；恢复后执行器重新注册 |
| PostgreSQL暂时不可用 | 当前页回滚，XXL显示失败并可重试 |
| 切换聚合/微服务模式 | 前端API地址不变，执行器只在当前模式注册一次 |

本方案不宣称Exactly Once。目标是“At-Least-Once调度 + 业务幂等 + 检查点 + fencing token”，在允许重复触发的前提下保证最终数据正确。

## 17. 面试口径

“我使用XXL-JOB统一管理SAP主数据同步的Cron、执行器路由、故障转移、超时、重试和调度日志。XXL-JOB只能保证调度层尽量不重不漏，无法保证业务数据只写一次，所以我在SRM侧保留运行记录、幂等键、分页检查点和数据库资源租约。节点失联后新实例通过递增fencing token接管，旧实例恢复也无法继续写入。失败重试从最后成功页继续，不重复全量扫描。”

简历表述建议：

“基于XXL-JOB建设SAP主数据分布式调度与失败补偿机制，结合PostgreSQL租约、fencing token、幂等键和分页检查点，实现多实例故障转移、断点续传及可视化运维。”
