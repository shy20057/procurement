# 供应商集中报价与截标并发控制技术方案

> 日期：2026-10-17。性质：待复现设计。
> 目标：供应商在报价截止前集中提交时，请求不重复、旧报价不覆盖新报价、截止判定明确且数据不泄露。
> 架构：基于现有RFQ多轮询价模型，Redis限制入口流量，PostgreSQL保证报价版本、幂等与截标互斥；提交先可靠落库，比较汇总异步生成。
> 技术基线：Java 17、Spring Boot 3.0.7、MyBatis-Plus、PostgreSQL、Redis、RabbitMQ，前端Vue 3。
> 实施约束：本轮只写方案；后续任何测试、联调、压测先征得用户批准，文中的容量场景是计划而非实测结论。

## 1. 客户背景与业务痛点

集团对工业控制器、设备维保服务等需求发起询价，邀请多家合格供应商参加。询价可能有多轮，供应商在每轮截止前可修订自己的价格、交付周期和商务说明，采购方在该轮截止后统一比较并形成定标结果。

一个采购集团可能同时开放多份RFQ。多家供应商在截止前集中提交，用户重复点击、浏览器超时重试及多标签页编辑会形成真实并发。单份RFQ供应商数量有限，不能把企业采购夸大成消费者秒杀；高负载来源应是多项目、多供应商、批量报价共同形成的峰值。

客户要求：

- 请求成功必须表示报价已经可靠保存，而非仅进入内存队列。
- 网络重试不生成多份报价，供应商可查询提交回执。
- 同供应商两个窗口同时修改时，旧版本不能静默覆盖新版本。
- 截止后禁止新的提交，客户端时间不能绕过截止限制。
- 一家供应商不能看到其他供应商报价，采购方按开价规则查看。
- 比价、统计和通知不拖慢提交，失败后可重建。
- 定标后可把批准的价格和交付条件落到价目表、货源信息或BPA。

首期规则：报价一旦成功提交立即生效，截止前可新版本覆盖；不建设独立草稿存储和密码学密封投标，不覆盖公共招标的完整法定流程。正式招标单`t_stc_tender_h`可复用并发机制，但本方案先实现RFQ询价，避免两套流程同时展开。

## 3. 业务流程与职责

```text
采购员创建RFQ与物料行 → 邀请供应商 → 发布本轮
  → 供应商身份校验 → 提交/修订报价 → 数据库保存并返回回执
  → Outbox通知与统计
  → 到截止点/采购员提前关闭 → 本轮CLOSED
  → 截止后比较各供应商最新报价 → 人工评审定标
  → 审核通过后发布定标事件 → 生成价目或BPA草稿
```

报价接受、轮次状态和最终有效版本均由`sourcing-service`决定。网关/Redis只控制访问流量，RabbitMQ只承担已落库之后的派生处理，不能作为截止时刻的最终裁判。

身份中的supplierCode由已验证的登录上下文提取，忽略请求体伪造的供应商编码。当前开发身份接口需要补充可靠的供应商用户映射和服务端校验，不能把浏览器自报角色作为权限依据。

## 4. 本轮规则和截止语义

新增轮次实体`rfq_round`，每轮状态为OPEN/CLOSED/CANCELLED，含精确的`deadline_at timestamptz`。RFQ现有日期字段仅兼容展示，实际写入校验以轮次实体为准。

接受规则明确为：事务取得轮次共享锁后，读取数据库实际时间；若OPEN且该时间严格小于deadline，则该提交可以被接受。该受理时刻写入回执。事务可能在截止后数毫秒提交，这仍然是有效受理，客户端到达网关的时间不作为承诺依据。

因此不承诺“截止前收到HTTP请求就一定接受”，也不以浏览器倒计时决定。请求排队到截止后才取得锁，会被拒绝。

已有date数据迁移成精确时间必须由管理员确认，例如Asia/Shanghai当日18:00；不能静默猜成23:59:59。新发布轮次必须显式填写带时区截止时间，后端统一转为Instant。

## 5. 数据模型

首期新增以下STC表：

```sql
create table stc_schema.rfq_round (
  rfq_id bigint not null references stc_schema.t_stc_rfq_h(id),
  round_no int not null,
  status varchar(20) not null,
  deadline_at timestamptz not null,
  closed_at timestamptz,
  version bigint not null default 0,
  primary key (rfq_id, round_no),
  check (status in ('OPEN','CLOSED','CANCELLED'))
);

create table stc_schema.rfq_invitation (
  rfq_id bigint not null,
  round_no int not null,
  supplier_code varchar(32) not null,
  status varchar(20) not null,
  primary key (rfq_id, round_no, supplier_code),
  foreign key (rfq_id, round_no) references stc_schema.rfq_round(rfq_id, round_no)
);

create table stc_schema.rfq_quote_head (
  id uuid primary key,
  rfq_id bigint not null,
  round_no int not null,
  supplier_code varchar(32) not null,
  current_version bigint not null default 0,
  last_accepted_at timestamptz,
  unique (rfq_id, round_no, supplier_code),
  foreign key (rfq_id, round_no) references stc_schema.rfq_round(rfq_id, round_no)
);

create table stc_schema.rfq_quote_revision (
  quote_id uuid not null references stc_schema.rfq_quote_head(id),
  version bigint not null,
  content jsonb not null,
  content_hash varchar(64) not null,
  accepted_at timestamptz not null,
  submitted_by varchar(80) not null,
  primary key (quote_id, version)
);

create table stc_schema.rfq_submission_receipt (
  id uuid primary key,
  supplier_code varchar(32) not null,
  idempotency_key varchar(100) not null,
  request_hash varchar(64) not null,
  quote_id uuid not null references stc_schema.rfq_quote_head(id),
  quote_version bigint not null,
  accepted_at timestamptz not null,
  response_json jsonb not null,
  unique (supplier_code, idempotency_key)
);
```

另外补`rfq_item`定义本轮采购行、物料、需求数量、币种和单位。物料编码不一定唯一，一张RFQ可能同物料不同交付地点，因此业务行使用不可变`rfq_item_id`。

现有`t_stc_rfq_e_quote`作为当前有效报价投影，新增`rfq_item_id/quote_head_id/quote_version/submitted_at`，唯一约束为`(header_id, round_no, supplier_code, rfq_item_id)`。历史修订保存在revision中，不在投影重复插入多版本。

迁移旧数据先报告重复和缺少行映射，不擅自删除。完成映射后再增加NOT NULL和唯一约束。现有展示DTO继续兼容，新增受限供应商DTO不含竞争对手数据。

消息复用03定义的STC `outbox_event/inbox_event`。如果先做本功能，先执行独立的`V2__business_messaging.sql`，无需等待BPA业务全部完成。

## 6. 提交接口与请求

```http
POST /api/stc/rfqs/1001/rounds/1/quotes:submit
Idempotency-Key: quote-request-demo-001
```

```json
{
  "expectedVersion": 0,
  "lines": [{
    "rfqItemId": 9001,
    "unitPrice": "1250.0000",
    "deliveryDays": 15,
    "minOrderQty": "10.0000",
    "packQty": "1.0000",
    "remark": "报价含约定交付条件"
  }]
}
```

返回201或200，内容含receiptId、quoteId、quoteVersion、acceptedAt。第一次提交expectedVersion为0，修订传当前版本；相同幂等键且请求摘要相同返回已保存回执，不创建新版本，截止后重试已成功请求也能取回原结果。

规范化摘要包括RFQ、轮次、当前用户供应商、expectedVersion、按rfqItemId排序后的内容。小数按既定精度规范化后计算SHA-256；不能直接对未经规范化、键顺序不固定的JSON字符串取哈希。

数量从RFQ行读取，报价金额由服务器计算；币种与询价行一致。首期每次提交该供应商本轮完整报价集合，不支持用缺失行隐含保留旧值；是否允许部分物料不报价需显式标记`NO_BID`，首期可限定所有行必报。

## 7. 提交事务与并发控制

处理顺序：

1. 验证身份、邀请关系、请求大小与字段格式；查询相同幂等键已成功回执，存在则按摘要返回。
2. 通过入口限流后打开数据库短事务，以`FOR SHARE`读取本轮，取得锁后单独读取`clock_timestamp()`判断截止与状态。
3. 在事务内重新验证邀请有效。撤销邀请操作也必须先取本轮排他锁，避免提交检查与撤销竞争。
4. 创建或找到该供应商报价头，用`expectedVersion`原子更新版本。
5. 写不可变revision、替换当前有效报价行、插入成功回执及Outbox。
6. 提交事务后返回已保存回执。任一失败整笔回滚，不返回“已提交”。

```sql
select status, deadline_at
from stc_schema.rfq_round
where rfq_id = :rfqId and round_no = :roundNo
for share;

-- 等待共享锁结束后才执行：不能用事务开始时间作截止判断
select clock_timestamp();

update stc_schema.rfq_quote_head
set current_version = current_version + 1,
    last_accepted_at = :acceptedAt
where id = :quoteId and current_version = :expectedVersion
returning current_version;
```

不同供应商的共享轮次锁互不排斥，各自更新自己的报价头；同供应商两个窗口基于相同旧版本提交，只有一个成功，另一个409并提示刷新。首个报价头以唯一键`INSERT ... ON CONFLICT DO NOTHING`创建，随后执行相同版本条件更新。

幂等键插入发生唯一冲突时，不在已失败的PostgreSQL事务里继续读：回滚该次事务，再从已提交回执读取并比较摘要。版本更新返回0行时也先回滚、查询该幂等键回执：同请求已经成功则返回原回执，确实没有成功回执才返回版本冲突。这样两个完全相同请求同时到达，即使后一个先碰到版本检查，也能得到同一个成功结果。不同业务请求误用同键返回409。

不使用一把RFQ级Redis独占锁串行所有供应商提交。数据库仍然有写入和索引成本，吞吐能力需实际测量；共享锁设计只是避免无必要的单项目全串行。

## 8. 截标与提前关闭如何竞争

关闭器以相同轮次行为协调点：

```sql
select status, deadline_at
from stc_schema.rfq_round
where rfq_id = :rfqId and round_no = :roundNo
for update;
```

拿到排他锁后，到期关闭器检查数据库当前时间是否已达到deadline；采购员提前关闭则校验权限和原因。然后在同一事务更新轮次为CLOSED、记录closed_at、写`RfqRoundClosed` Outbox。

已有提交持有共享锁时，关闭器等这些短事务完成；关闭成功后新的共享读取看到CLOSED并拒绝。即使关闭器因为定时任务延迟尚未运行，提交接口仍独立检查deadline，所以不会延迟放行。

所有关轮、取消RFQ、改变截止时间、撤销邀请的写路径都必须走同一协调规则，不能绕开轮次锁直接更新表。首期不允许在OPEN状态任意缩短截止时间，延长或重开通过显式业务命令及审计完成。

同类共享/排他锁的冲突关系参考[PostgreSQL行锁说明](https://www.postgresql.org/docs/current/explicit-locking.html)。数据库`now()`取事务开始时刻，`clock_timestamp()`用于这里的实际受理时刻，依据[时间函数说明](https://www.postgresql.org/docs/current/functions-datetime.html)。

## 9. 限流、缓存与降级

Redis按“已认证supplierCode + RFQ”做原子令牌桶/滑动窗口，例如每秒2次、允许突发5次；这是起始配置，按业务调整。超过限制返回429和Retry-After，不以异常堆栈回应。

同时限制请求体1MB、每次最多200行，附件单独上传并引用对象ID。提交不在事务里上传文件、调用SAP或跨服务远程查供应商。

Redis失败时采用本机有界并发和较保守的入口限速，业务唯一约束、版本、截止仍由数据库保证。不能把Redis无记录当作没有提交过。

缓存RFQ物料与静态条款可降低读取成本，但提交最终规则在数据库事务内校验。数据库不可用则返回失败或503，不能只写Redis后告诉供应商报价已保存。

## 10. 异步比价、定标与保密

报价提交事件路由`stc.quote.submitted.v1`，消费者更新通知或供应商自己的提交状态。开放期间不在公开缓存、日志或消息管理界面暴露竞争对手价格。

轮次关闭事件路由`stc.rfq.round-closed.v1`。比价消费者确认轮次CLOSED后查询该轮每个供应商最新报价快照，生成可重建的比较结果。不能只根据已收到的报价消息认定数据齐全，因为MQ可能乱序；当前有效报价表才是本轮数据真相。

报价修订事件携带quoteId和quoteVersion，派生投影只接受更高版本；通知去重使用inbox。最终定标需人工评审、权限和审批，不能自动把最低价等同于中标。

定标审核后以`awardId + awardVersion + targetType`唯一生成价目/BPA草稿，不直接生效为正式协议。最低起订量、包装量、交付周期随定标快照带出，对应原实习货源清单反写场景。

权限要求：

| 用户 | 可见范围 |
| --- | --- |
| 供应商 | 邀请给自己的RFQ与自身报价、回执，不见其他供应商 |
| 采购员 | OPEN期间看提交状态；CLOSED后按权限看报价与比价 |
| 评审人员 | 只看授权项目，操作有审计 |
| 运维人员 | 默认只见运行状态与脱敏错误，不自动获得报价金额权限 |

这套访问控制不等于加密密封投标。若客户要求“数据库管理员在开标前也无法读取报价”，需要单独设计密钥托管与解密审批，超出首期范围。

| --- | --- |
| 同键同请求并发重试 | 一个成功版本、一张回执，后续取回同结果 |
| 同键不同报价 | 409，既有报价不变 |
| 两个窗口基于版本3修订 | 一个成为4，另一个版本冲突 |
| 多个供应商同时提交 | 报价互不覆盖，不因共享轮次锁全串行 |
| 截标与提交同时竞争 | 符合第4节受理时刻规则，没有关闭后新受理 |
| 关闭器延迟一分钟 | 提交仍按deadline拒绝 |
| 事务等待跨越截止 | 取得锁后读取实际时间并拒绝 |
| Redis不可用 | 限流降级，数据库仍保证业务正确 |
| 越权修改supplierCode/receiptId | 无法读取或修改其他供应商报价 |
| 消息重复、关闭事件先到 | 比价读取已提交数据库快照，可重建 |

获批后以多个RFQ、供应商身份隔离的数据集测试，分别观察提交TPS、P95/P99、数据库锁等待、409业务冲突、429限流、错误率与异步延迟。报告需区分“成功接受报价”“有效业务拒绝”和“系统错误”，不能把所有HTTP返回都当吞吐成功。

安全验收包含采购详情响应过滤、供应商横向越权和报价日志脱敏；测试数据不可使用实际客户敏感报价。所有指标待执行后记录，不提前写“支持万级并发”。

## 15. 面试讲解与简历口径

“集团多个询价项目在截止前出现供应商集中提交，主要风险是重复报价、旧版本覆盖、截标竞争和报价泄露。我使用数据库业务唯一键与回执保证重试幂等，用报价版本控制并发修订；提交共享锁与关闭排他锁协调截止状态，并在取得锁后按数据库时间判断受理。报价先可靠保存，通知和比价异步处理。”

复现完成后可写：“实现供应商多轮询价提交，基于幂等回执、版本控制和截止状态锁处理重复与并发修订，结合Redis限流及异步比价支撑集中报价场景。”原实习涉及报价数据联动，个人复现完成并发提交增强，两部分经历明确区分。
